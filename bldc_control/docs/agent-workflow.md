# Agent Workflow

本文件细化入口规则中的工作原则、执行流程和项目分析重点。处理代码、配置、文档或调试任务时按需读取；授权与高风险执行边界以入口文件和 `risk-and-tools.md` 为准。

## 工作原则

- 严格从原始需求出发，不擅自扩展范围或增加未经请求的功能。
- 只勘察任务相关的代码、配置、文档和错误信息，理解受影响的架构、依赖与业务语义，不做无关的全项目勘察。
- 保持既有架构、公共接口兼容性和实现风格；优先使用已有依赖、标准库与原生能力，避免过度抽象。
- 用户明确要求修改、修复、实现、创建或删除时，直接实施并验证范围内已授权的可逆本地变更；仅要求计划、分析、解释、诊断、Review 或状态时，只读检查，不修改环境。
- 跨模块、公共接口或数据模型改动先说明方案、影响和验证方式；大范围重构或架构调整补充替代方案和回滚方式。范围明确且已授权的可逆本地修改继续实施，不因“跨模块”本身重复确认。
- 低风险、可逆且不改变目标的不确定事项可明确假设后继续；无法从需求确定、会显著影响结果、兼容性或风险的关键选择先确认。等待期间继续不依赖该答案的已授权工作。
- 发现安全、数据一致性、性能或架构隐患时，先完成主需求，再单独列出风险和建议；重大风险可先暂停说明。

## 执行流程

1. 明确目标：识别核心问题、输入输出和约束，建立可验证的验收标准。
2. 快速勘察：先获取摘要，再按需读取相关上下文，保护用户已有改动。
3. 制定方案：多步任务给出简短步骤与验证项；小任务直接执行。
4. 实施变更：采取最小必要修改；需要扩大范围或涉及未授权的重要兼容性、数据、安全、成本影响时，仅确认受影响部分。
5. 静态自检：业务逻辑或数据流变化沿“入口 → 核心逻辑 → 边界/异常 → 出口”检查；文案或样式修改不扩展为完整业务链路审查。
6. 验证结果：遵循 `testing-and-validation.md`，按范围和风险做最小充分验证，不默认全量构建或真实环境联调。
7. 完成交付：实现用户要求、完成必要验证并修复本次改动造成的问题后交付，不追加无关重构或美化。遇到阻塞时说明已完成内容、具体阻塞和所需信息，不反复盲目重试。

## 项目分析重点

仅在接手或初始化项目等确需整体理解时，按目标选择以下检查项，不将其作为普通局部改动的全量清单：

- 技术栈、目录结构、架构分层和模块边界。
- 依赖、配置、环境变量和构建/部署流程。
- 核心业务流程、数据模型、接口契约和权限边界。
- 代码质量、重复逻辑、异常处理、日志、性能瓶颈和安全风险。
- 测试覆盖、文档完整性和可维护性。
